# Task-to-PR Platform — Agent Configuration

> Read this file before executing any step in any task. It applies to all agents: Claude, Codex, Gemini, and any other AI runtime operating in this repository.

---

## What this is

A **generic task-to-PR platform**: a fixed set of reusable skills that take any natural-language
task and drive it to a reviewed pull request — plan, config, scaffold, implement, demo, test,
gate, PR. Nothing here is tied to a specific product or feature domain. The only per-task piece
is the generated `implement-<feature>` skill; every other step is reusable as-is.

**Repository layout:**

```
src/
  components/     UI components (if the feature has a UI)
  lib/            Business logic modules
  api/            Request handler functions
  config/         loadConfig.ts — runtime config reader
  demo/           Local demo server (generated by wire-demo-app when demo.enabled)
config.json       Non-secret config (committed, generated by generate-config)
.env.example      Env var names with empty values (committed)
.env              Secrets + local overrides (gitignored, user fills)
.agents/
  AGENTS.md       ← you are here
  skills/         One skill per automation step
  features/       Feature-specific context files (generated per feature)
```

All skill paths use the `.agents/` prefix. Always reference them as `.agents/skills/<name>/SKILL.md`.

## The Task-to-PR Loop

Every task — regardless of feature type — follows this loop:

```
Task description
      │
      ▼
 [plan-task]              → plan, config_requirements, acceptance criteria
      │ ↓ [wait for approval]
      ▼
 [generate-config]        → append-only config.json + .env.example
      │
      ▼
 [bootstrap-project]      → toolchain setup (greenfield only)
      │
      ▼
 [scaffold-feature]       → typed file/folder stubs
      │
      ▼
 [implement-<feature>]    → working implementation reading loadConfig()
      │
      ▼
 [wire-demo-app]          → local HTTP demo server (when demo.enabled)
      │
      ▼
 [write-tests]            → unit + integration tests
      │
      ▼
 [verify-local]           → smoke test against demo server (when demo.enabled)
      │
      ▼
 [run-acceptance-gate]    → gate result: PASS or ESCALATE
      │
      ▼
 [document-feature]       → delivery report + screenshots (when demo.enabled)
      │
      ▼
 [create-pr]              → conventional commit + GitHub PR
```

**The `implement-<feature>` step is the only step that changes per task.** All other steps
are reusable as-is. To support a new feature type, add a new `implement-<feature>` skill and
register it in the Skill Index below.

## Config: how it works

Project configuration lives at the **repo root** — not under `.agents/`:

| File | Committed | Purpose |
|------|-----------|---------|
| `config.json` | Yes | Non-secrets: endpoints, ports, feature flags, URL templates |
| `.env.example` | Yes | Documents env var names with empty values |
| `.env` | **No** (gitignored) | Secrets + local overrides the user fills |

**`generate-config` writes these files** during the loop after plan approval. It is
**append-only**: existing keys are never overwritten. Running `task2pr` for a new feature
adds new keys without touching values already set by the user.

Application code reads all config through `src/config/loadConfig.ts`, which:
1. Reads `config.json`
2. Overlays `process.env` (env wins for secrets)
3. Expands `${ENV_VAR}` placeholders in string values

**No `.agents/providers/` folder exists.** The agent's knowledge of well-known external-service
endpoint patterns is applied by `generate-config` at task time — those templates are written
into `config.json`, not stored as committed preset files.

## Agent Rules

1. **Read the skill file before executing that step.** Do not execute from memory.
2. **Do not skip steps.** The acceptance gate is the stop condition — skipping it makes the loop unsafe.
3. **One PR per task.** If a task is too large for a single PR, split it before proceeding.
4. **Escalate, don't guess.** If the gate fails after 3 fix cycles, stop and report the exact failing items.
5. **Sensitive logic requires a test.** Any change touching security, money, data integrity, or access control must ship with a corresponding test. This is non-negotiable.
6. **Config, not code, for all external values.** Endpoint URLs, client IDs, cookie names, port numbers, and every environment-specific value must come from `loadConfig()`. Never hardcode them in source.
7. **Config writes are append-only.** `generate-config` only adds keys that are missing. It never reads and overwrites an existing value.
8. **No secrets in committed files.** `config.json` holds non-secret settings only. Secrets go in `.env` (gitignored).
9. **No `.agents/providers/` folder.** External-service URL knowledge lives in `generate-config`. New services = new keys in config, not new preset files.
10. **Skills are the extension point.** A new feature means a new `implement-<feature>` skill. The loop steps stay fixed.

## Extending This Loop

To add a new feature type:

1. Create `.agents/skills/implement-<your-feature>/SKILL.md` following the same frontmatter structure as existing skills.
2. Create `.agents/features/<your-feature>/CONTEXT.md` with domain context, flow diagram, and acceptance criteria.
3. Add a row to the Skill Index above.
4. Reference `.agents/features/<your-feature>/CONTEXT.md` from inside the skill.

The loop steps do not change. Only the implement step swaps.

## Production Scaling Path

| Current (demo) | Production addition |
|----------------|---------------------|
| Manual task input | Task ingested from Linear / Jira via a `fetch-task` skill |
| Feature skills generated on demand | Many `implement-*` skills mapped to feature types in a router |
| Manual gate run | CI enforces gate items on every push; PR merge blocked until green |
| No audit trail | `commit-log` skill writes to a feature ledger |
| Single external service per feature | Multiple entries in `config.json` with runtime selection |
